Portfolio Project Roadmap

EventForge

A Kafka-based distributed job processing platform in TypeScript — from modular monolith to independently deployable services. Twenty-four milestones, each independently buildable and committable.

Stack: Fastify · PostgreSQL · Prisma · Kafka (KafkaJS) · Zod · Jest · Testcontainers · Pino · Prometheus/Grafana · React

Where I'd adjust your plan

The architecture you laid out is already sound — these are refinements, not objections.

  • Tiered retry topics, not one. Use jobs.retry-1 / jobs.retry-2 / jobs.retry-3 with per-tier delay, rather than a single retry topic. You can see backlog-per-tier in monitoring, and a job stuck at tier 3 is a meaningfully different signal than one at tier 1. Detailed in Milestone 11.
  • Isolate event contracts from Milestone 6, not at extraction time. Build src/contracts (envelope + zod schemas + schema versions) as its own internal module the moment Kafka is introduced. At extraction (M18) it becomes packages/event-contracts with zero rewrite — that's the whole payoff.
  • Enforce module boundaries from day one, not just validated at M17. Wire dependency-cruiser or eslint-plugin-boundaries in Milestone 1, set to error-level immediately. Retrofitting a boundary rule onto code that already violates it is far more expensive than starting with the guardrail on.
  • Execution must never touch the Job table, even pre-extraction. Only the jobs module's own status consumer writes Job.status, from day one in the monolith. This is what makes the M18 extraction a deployment change instead of a rewrite — build the discipline before there's a network boundary to enforce it.
  • Prisma has no native SELECT ... FOR UPDATE SKIP LOCKED. You'll need $queryRaw for the outbox publisher's row-claiming in Milestone 9 — flagging this now so it doesn't stall you mid-milestone.
  • Add a thin CI loop from Milestone 1 (lint + typecheck + unit tests on every push), not just at Milestone 24. Full build/deploy pipelines stay at the end; fast feedback shouldn't wait that long.
  • Two different "idempotency" concepts share a word, not a table. The Idempotency-Key HTTP header (M5, duplicate job submission) and Kafka consumer idempotency via ProcessedEvent (M10, duplicate event delivery) solve different problems — keep them as separate tables and separate mental models.
  • Job timeouts needed an explicit home — your spec listed them as a reliability requirement but didn't attach them to a milestone. Folded into Milestone 11 as a watchdog alongside retry/DLQ, since a timeout is really just another path into the failure/retry pipeline.

Cross-Cutting Decisions

These are fixed once and referenced by every milestone below, rather than re-litigated each time.

Job state machine

Enforced in exactly one place: Job.transitionTo() in modules/jobs/domain/job.entity.ts. Every API route and every Kafka consumer that changes a job's status goes through the jobs module's own service/repository, which calls this method — nothing else is permitted to write the status column directly. This is a discipline choice, not a framework feature, and it's what makes the execution extraction (M18) safe.

Event envelope

Every Kafka message uses this shape, defined once in src/contracts/envelope.ts (later packages/event-contracts). Message key is always the jobId, so all events for one job stay in the same partition and are processed in order.

{
  "eventId":       "uuid",
  "eventType":     "JobRequested" | "JobStarted" | "JobCompleted" | "JobFailed" | "...",
  "aggregateId":   "jobId",
  "correlationId": "uuid — same value for one job's entire lifecycle",
  "causationId":   "uuid | null — eventId of the event that triggered this one",
  "occurredAt":    "ISO-8601 timestamp",
  "schemaVersion": 1,
  "payload":       { /* event-specific, zod-validated per schemaVersion */ }
}

Phase 3 — Reliability
09Transactional outboxJob + JobRequested committed atomically; a polling publisher moves rows to Kafka.

Features

  • OutboxEvent table; Job creation and outbox insert happen in one Prisma transaction
  • Polling publisher: claims unpublished rows, sends to Kafka, marks publishedAt

Architectural decisions

Row claiming for concurrent publishers needs SELECT ... FOR UPDATE SKIP LOCKED, which Prisma Client has no first-class API for — use $queryRaw. Explicitly document the residual gap: if the process crashes after Kafka send() acks but before the publishedAt UPDATE commits, the row is retried and the event is sent twice. The outbox guarantees at-least-once, never exactly-once — that's precisely why consumers must be idempotent (M10).

10Idempotent consumersMake redelivery from the outbox's at-least-once guarantee safe.

Features

  • ProcessedEvent(eventId, consumerName) with a unique constraint on the pair
  • Reusable idempotent-consumer wrapper: insert-or-skip → apply business change → create outbox events → commit → then commit the Kafka offset

Architectural decisions

The unique constraint is what makes concurrent redelivery (e.g. a brief overlap during a rebalance) safe: two processes racing to insert the same (eventId, consumerName) — the DB serializes it, the loser's insert fails, and it no-ops instead of double-applying. Disable Kafka auto-commit (autoCommit: false); commit offsets manually only after the DB transaction succeeds.

Scope Definitions

Minimum viable version

Milestones 1–12. A working modular monolith: REST API, Postgres persistence, transactional outbox, idempotent Kafka consumers, tiered retry with dead-lettering, and cancel/manual-retry — no extraction, no dashboard, minimal observability. This alone demonstrates every core reliability pattern.

Fully developed portfolio version

All 24 milestones. Three services extracted from the monolith with database-per-service and documented eventual consistency, full observability stack, hermetic Testcontainers CI, a React ops dashboard, a load-test writeup, and a CI/CD pipeline — deliberately stopping short of Kubernetes.
