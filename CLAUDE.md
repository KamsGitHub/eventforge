# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

EventForge: a Kafka-based distributed job processing platform in TypeScript, built as a milestone-by-milestone portfolio project. It starts as a modular monolith and is incrementally evolved into independently deployable microservices. The full plan — every milestone's objective, architectural decisions, database/Kafka changes, tests, and completion criteria — lives in `docs/roadmap.html` (open it in a browser; it's a long, self-contained reference doc, not something to read via `cat`).

**Always check `docs/roadmap.html` for the current milestone's scope before adding features.** Each milestone explicitly states what should _not_ be built yet — respect that; don't pull forward work from a later milestone (e.g. don't wire real Kafka/Postgres logic before Milestone 6/9 says to) even if it seems convenient.

## Commands

```bash
npx prisma generate    # regenerate the Prisma client into generated/ (gitignored; run after clone/schema change)
npm run dev            # tsx watch src/server.ts — http://localhost:3000/health
npm run lint           # ESLint (flat config, type-aware)
npm run typecheck      # tsc --noEmit against tsconfig.json (src + tests + prisma.config.ts)
npm run boundaries     # dependency-cruiser module-boundary check — see below
npm test               # Jest — both the "unit" and "integration" projects (see Milestone 15)
npm run test:unit      # Jest, "unit" project only — no Docker required, ~5s
npm run test:integration  # Jest, "integration" project only — needs Docker, see Milestone 15
npm run build          # tsc -p tsconfig.build.json, then tsc-alias rewrites @/ aliases in dist/
npm start              # node dist/src/server.js (run npm run build first)
npm run format         # prettier --check .
npm run format:write   # prettier --write .
```

Run a single unit test file: `npx jest --selectProjects unit tests/smoke.test.ts`. Run a single integration test file: `npm run test:integration -- tests/integration/jobs/prisma-job.repository.test.ts` (a bare `npx jest <path>` skips the `cross-env`-set `NODE_OPTIONS` flag below and the right `--selectProjects`, so prefer the npm script form). Run tests matching a name: `npx jest -t "some test name"`.

CI (`.github/workflows/ci.yml`) runs lint → typecheck → boundaries → test:unit → test:integration on every push/PR against `main`, on Node 22 (Milestone 15 split the old single `npm test` step in two, so cheap unit-test feedback doesn't wait on Docker). **`npm run boundaries` requires Node ^22||^24||>=26** (a `dependency-cruiser` constraint) — this already broke CI once when the workflow was pinned to Node 20; don't drop the Node version below that.

**Every Jest command needs `NODE_OPTIONS=--experimental-vm-modules`** (set via `cross-env` in the `test`/`test:unit`/`test:integration` scripts, for Windows/cross-shell portability) — required by Prisma 7's driver-adapter runtime, not optional; removing it breaks every test that touches a real `PrismaClient` with a cryptic "dynamic import callback was invoked without --experimental-vm-modules" error. This bit repeatedly during Milestone 15 development specifically when reaching for a bare `npx jest <path>` to isolate a failing suite — it doesn't fail loudly, it just makes `OutboxPublisher.pollOnce()` (or any other real-Prisma call) throw that TypeError on literally every call, which from the outside looks exactly like a hang if something's polling it in a loop. Always run integration tests through `npm run test:integration`, never bare `npx jest`.

**`npm run test:integration` needs a working Docker daemon.** `jest.config.js` splits the suite into two Jest **projects** (`unit`/`integration`, selected via `--selectProjects`) specifically so `tests/integration/**` gets its own `globalSetup`/`globalTeardown` (`tests/integration/global-setup.ts` / `global-teardown.ts`, delegating to `tests/integration/setup.ts`) without unit tests paying for it. See Milestone 15 below for what that setup actually does and the sharp edges it introduces.

**`@/*` path aliases don't resolve at runtime in compiled output** — `tsc` alone leaves `require('@/app')` in `dist/`, which Node can't resolve. `npm run build` runs `tsc-alias` afterward specifically to rewrite those to relative `require()` paths; don't remove that step or add a new build path that skips it.

### Local infrastructure (Milestone 2)

`docker-compose.yml` at the repo root runs Postgres 16 and Kafka (`apache/kafka:4.3.1`, KRaft mode, no ZooKeeper) plus a one-off `kafka-init` job and an optional `kafka-ui`. Bring it up with `docker compose up -d postgres kafka && docker compose up kafka-init`. The 8 topics (`jobs.requested/started/completed/failed`, `jobs.retry-1/2/3`, `jobs.dead-letter`) are created explicitly by `infrastructure/kafka/create-topics.sh` — **never add reliance on broker auto-create**; if a new topic is needed, add it to that script's `TOPICS` array. `src/` started actually consuming/producing at Milestone 7 (see below) — before that, the topics existing didn't mean they were wired into the app.

### App vs. server split (Milestone 3)

`src/app.ts` exports `buildApp(deps)`, which builds and returns a Fastify instance — it never calls `.listen()`. This is what lets tests use `app.inject()` without binding a port. `src/server.ts` is the only side-effecting entrypoint: it loads `.env` via `dotenv/config`, calls `buildApp()`, `.listen()`s, and wires `SIGINT`/`SIGTERM` to `app.close()` before `process.exit()`. **Any new route or plugin goes in `app.ts` (or a module's `api/`), never in `server.ts`.**

Config is loaded once via `loadConfig()` in `src/config/env.ts` (zod-validated, defaults for missing vars, throws on invalid ones) and attached to the Fastify instance as `app.config` — modules read `app.config`, they don't call `process.env` directly. `NODE_ENV`, `PORT`, `LOG_LEVEL`, and (since Milestone 4) `DATABASE_URL` are validated; extend `envSchema` when a milestone actually starts consuming a new var (e.g. `KAFKA_BROKERS` at Milestone 6), rather than adding it speculatively.

The pino logger (`src/shared/logger.ts`) is passed into Fastify via the `loggerInstance` option (not `logger` — Fastify 5 uses `loggerInstance` specifically for a pre-built logger instance).

### Prisma / database (Milestone 4)

This project is on **Prisma 7**, which changed enough that assumptions from Prisma 4–6 don't hold:

- **Driver adapters are mandatory.** `datasource.url` in `prisma/schema.prisma` is gone entirely (`url = env(...)` is now a hard schema-validation error) — the connection string lives in `prisma.config.ts` (`datasource.url: process.env['DATABASE_URL']`), and `PrismaClient` requires an `adapter` (we use `@prisma/adapter-pg`'s `PrismaPg`). There is no "classic" no-adapter mode to fall back to.
- **The generator is `prisma-client` (not `prisma-client-js`)**, outputting real `.ts` source — not a prebuilt package — to `generated/prisma/` (gitignored; run `npx prisma generate` after cloning or changing the schema). We pinned `moduleFormat = "cjs"` in the generator block in `prisma/schema.prisma`; without it, the generator emits ESM (`import.meta.url`), which breaks under our CommonJS/ts-jest setup.
- **`src/db/prisma-client.ts` vs `src/db/prisma.ts` is a deliberate split, not duplication.** `prisma-client.ts` is side-effect-free: it just re-exports `PrismaClient`, `Prisma`, `PrismaJobRow`, and a `createPrismaClient(url?)` factory. `prisma.ts` is the actual singleton: `export const prisma = createPrismaClient()` runs `loadConfig()` at module load time, which throws without a live `DATABASE_URL`. **Anything that only needs the client type/factory (tests constructing their own client, e.g. against a Testcontainers database) must import from `prisma-client.ts`, not `prisma.ts`** — importing the latter for its types would still eagerly execute the singleton line and crash without `DATABASE_URL` set.
- Jest's `moduleNameMapper` strips a trailing `.js` from relative imports (`^(\.{1,2}/.*)\.js$`) because the generated client uses NodeNext-style `./foo.js` imports against `.ts` source files with no compiled `.js` on disk — without the mapping, Jest can't resolve them.
- `.dependency-cruiser.cjs`'s `doNotFollow` excludes `^generated` (alongside `node_modules`) — otherwise the boundary/circular check cruises into the generated client's own internal circular references, which aren't ours to fix.

### Job persistence (Milestone 4)

`modules/jobs/domain/job.entity.ts` is the `Job` aggregate: immutable (`transitionTo()` returns a new `Job`, never mutates), with the state machine's legal transitions as its only enforcement point (throws `IllegalJobStateTransitionError` from `domain/errors.ts` otherwise). `JobStatus` lives in its own `domain/job-status.ts` file specifically to avoid a circular import between `job.entity.ts` and `errors.ts` (both needed the type; extracting it broke the cycle instead of one importing from the other).

`modules/jobs/infrastructure/prisma-job.repository.ts` is **the only file in the jobs module allowed to import the Prisma client** — this is the seam the execution-service extraction (Milestone 18) cuts along. Optimistic concurrency: `update()` does `updateMany({ where: { id, version }, data: { ..., version: { increment: 1 } } })` and throws `JobVersionConflictError` if `count === 0` — it does not trust the entity to have bumped its own version; the entity's `transitionTo()` never touches `version` at all, by design (version is purely a persistence-layer concern, closer to how JPA's `@Version` works than something the domain reasons about).

### Job API and composition root (Milestone 5)

`src/app.ts` no longer constructs its own dependencies — `buildApp({ config?, jobService })` requires a `JobService` to be passed in. **`server.ts` is the composition root**: it's the only place that imports the real `prisma` singleton and `PrismaJobRepository`, wires them into a `JobService`, and hands that to `buildApp()`. This keeps `app.ts` free of any eager Prisma singleton import (importing `@/db/prisma` anywhere triggers its `loadConfig()` call — see above) and keeps tests able to pass an `InMemoryJobRepository`-backed `JobService` instead. **If you add a new module's routes, follow the same pattern**: the module's `api/routes.ts` takes a service instance as a parameter; `server.ts` wires the real one, tests wire a fake one — `app.ts` itself stays ignorant of which.

Request validation/serialization goes through `fastify-type-provider-zod` (`validatorCompiler`/`serializerCompiler` set once in `app.ts`, `.withTypeProvider<ZodTypeProvider>()` on the instance) — route schemas are the same zod schemas from `modules/jobs/api/schemas.ts`, reused rather than re-declared, so they're ready to feed an OpenAPI generator later. **`modules/jobs/api/routes.ts` has a `FastifyBaseLogger`-vs-concrete-pino-instance generic mismatch** (same root cause as the `app.ts` return-type issue from Milestone 3, now surfacing at the `registerJobRoutes` call site instead) — worked around with a local `AppInstance` type alias that sets the Logger generic to `any` deliberately (documented inline). Don't try to make it structurally exact; it's a known Fastify+custom-logger+generic-method variance quirk, not a bug in our code.

`PrismaJobRepository.create()` translates Prisma's `P2002` unique-constraint error (on `idempotencyKey`) into a domain-level `DuplicateJobSubmissionError` — `JobService.createJob()` catches that and returns the existing job via `findByIdempotencyKey()` instead of erroring. This is the HTTP-level duplicate-submission guard (client-supplied `Idempotency-Key` header) — keep it separate from the Kafka `ProcessedEvent` idempotency table arriving at Milestone 10; different mechanism, different table.

### Kafka producer/consumer foundation and event contracts (Milestone 6)

`src/messaging/{kafka-client,producer,consumer}.ts` are thin KafkaJS wrappers, not a framework: `createKafkaClient({ brokers, clientId })` builds the shared `Kafka` instance, `createProducer()` returns an idempotent producer (`idempotent: true` — KafkaJS then requires `acks: -1`, which is already its default, so it's left implicit rather than re-specified per call), and `createConsumer(kafka, { topic, groupId, handler })` connects, subscribes, and starts `run()` in one call, returning the `Consumer` for the caller to `disconnect()`. `KAFKA_BROKERS`/`KAFKA_CLIENT_ID` are validated in `envSchema`.

`src/contracts/envelope.ts` + `src/contracts/events/*.ts` are the event envelope and per-event zod schemas (`JobRequested/Started/Completed/Failed`, each schema-versioned as `...SchemaV1`), built now specifically so they're ready before the outbox (M9) and idempotent consumption (M10) need them — see the roadmap's cross-cutting "Event envelope" section for the exact wire shape this mirrors.

**Testcontainers + Kafka gotcha, worth knowing before reaching for `@testcontainers/kafka` again**: its `KafkaContainer` only works with Confluent images (its KRaft bootstrap script targets `/etc/confluent/docker/*`) — it's incompatible with the `apache/kafka:4.3.1` image `docker-compose.yml` uses, so Kafka integration tests use `confluentinc/cp-kafka:7.5.0` instead, purely to get a hermetic broker. Also, its **default wait strategy only waits for the TCP port to accept connections**, which fires while the JVM is still initializing — connecting that early gets an immediate `ECONNRESET` on the first real request. Fixed with an explicit `.withWaitStrategy(Wait.forLogMessage(/Kafka Server started/))` so `.start()` doesn't resolve until the broker can actually serve requests. (See the `npm test`/`maxWorkers` note above for the other Testcontainers gotcha this milestone surfaced.)

### Basic asynchronous job execution (Milestone 7)

The `execution` module's first real Kafka wiring: `modules/execution/domain/job-handler.port.ts` defines `JobHandler.execute(payload): Promise<unknown>`; `modules/execution/application/execute-job.service.ts` is a registry (`ReadonlyMap<jobType, JobHandler>`) that throws `UnknownJobTypeError` for an unregistered type; `modules/execution/infrastructure/jobs-requested.consumer.ts` consumes `jobs.requested`, calls the registry, and publishes `JobCompleted` (success) or `JobFailed` (any thrown error, `attempt` hardcoded to `1` — no retries until later) directly to Kafka — **no outbox on this outbound side yet, that's M9's concern, and it never touches the Job row** (see the cross-cutting rule: execution only ever publishes events). `GenerateReportHandler` (`domain/handlers/generate-report.handler.ts`) is the one registered handler so far; it zod-validates `{ reportName: string }` and rejects (deliberately, to give the failure path something real to exercise) when that's missing or the wrong type.

**`server.ts` now constructs the first real `Kafka`/`Producer`/`Consumer` instances** — a `createKafkaClient` from `app.config.kafkaBrokers`/`kafkaClientId`, a producer connected at startup, and `startJobsRequestedConsumer(...)` — and disconnects both in `shutdown()` before `app.close()`. This corrects an earlier (wrong) assumption in this file that Kafka wiring in the composition root starts at M9/M10: the outbox (M9) and consumer idempotency (M10) are refinements of flows that go live here and at M8, not the first time a connection exists. **`JobService.createJob()` still doesn't publish anything** — jobs created via the HTTP API stay `PENDING` forever until M8 wires `JobService.create` to actually produce `JobRequested`; only a manually-published `JobRequested` event (e.g. from a test or script) flows through today.

### Job lifecycle events and status updates (Milestone 8)

Closes the loop: the full `jobs.requested → jobs.started → jobs.completed|failed` workflow now runs end-to-end, at-most-once (no outbox, no consumer idempotency yet — those are M9/M10). Two things now happen that didn't before:

- **`JobService.createJob()` really publishes.** After the row is inserted `PENDING`, it builds a `JobRequested` envelope and does a **direct `producer.send`** (via the shared `publish()` helper) — still no outbox, exactly the gap M9 closes — then immediately transitions the job to `QUEUED` and persists that via `JobRepository.update()`. `JobService`'s constructor now takes a `Producer` as a second argument alongside the repository. **Superseded at M9** — see below: the direct `producer.send` and the immediate `QUEUED` transition are both replaced by the outbox.
- **Execution publishes `JobStarted`** in `jobs-requested.consumer.ts`, unconditionally, before invoking the handler (not inside the try/catch that produces `JobCompleted`/`JobFailed` — a start notification isn't a handler outcome).

**`modules/jobs/infrastructure/job-status.consumer.ts`** is the jobs module's own status consumer — the _only_ writer of `Job.status`, per the cross-cutting rule below. It subscribes to `jobs.started`/`jobs.completed`/`jobs.failed` on one consumer group and calls `Job.transitionTo()` accordingly (`RUNNING` / `SUCCEEDED` with `result` / `FAILED` with `error`). This needed `createConsumer()` (`src/messaging/consumer.ts`) to accept `topic: string | readonly string[]` — previously single-topic-only — since one consumer group here legitimately needs three topics, not three separate consumer groups each independently rebalancing.

**Not yet, deliberately**: redelivery of an already-applied `jobs.started`/`completed`/`failed` event throws `IllegalJobStateTransitionError` (e.g. re-consuming `jobs.started` after the job is already `RUNNING`) rather than being ignored — this is the "duplicate events currently double-apply" gap the roadmap calls out, fixed by consumer idempotency at M10, not worked around here.

`tests/integration/e2e/job-lifecycle.e2e.test.ts` is the first true end-to-end test: real Postgres + real Kafka (both via Testcontainers), the full `buildApp()`, both consumers, and both the execution module's handler and the jobs module's status consumer wired together — POSTs a job via `app.inject()`, polls GET until terminal, and asserts the final state/timestamps for both the success and failure paths.

### Transactional outbox (Milestone 9)

Removes the M8 direct `producer.send` from job creation — that was the exact "crash between insert and publish loses the event" gap this milestone closes. `JobService` drops its `Producer` dependency entirely and goes back to `constructor(jobs: JobRepository)`.

- **`OutboxEvent` model** (`prisma/schema.prisma`, table `outbox_events`): `id, aggregateId, eventType, topic, messageKey, payload (jsonb), createdAt, publishedAt (nullable), publishingAttempts, lastError`. The unpublished-rows index is **hand-written raw SQL in the migration** (`WHERE "publishedAt" IS NULL`) — Prisma's schema DSL has no partial-index syntax, so `schema.prisma` only declares a plain `@@index([createdAt])` to keep `prisma migrate dev` from treating the hand-added `WHERE` as drift it should revert; expect to re-edit that clause back in if a future `prisma migrate dev` regenerates this index.
- **`JobService.createJob()` now calls `JobRepository.createWithOutboxEvent(job, outboxEvent)`** instead of `create()` — `PrismaJobRepository`'s implementation wraps `tx.job.create` + the shared `insertOutboxEvent(tx, event)` (from `src/outbox/outbox.repository.ts`) in one `prisma.$transaction`. The job stays `PENDING`; nothing transitions it to `QUEUED` at creation time anymore (see below).
- **`src/outbox/`** is deliberately module-agnostic (like `src/messaging/`), not jobs-specific, so other modules can grow their own outbox use later without teaching this code what a "Job" is:
  - `outbox.repository.ts`: `insertOutboxEvent` (works against either a plain `PrismaClient` or a `Prisma.TransactionClient`), and `claimNextUnpublished(tx)` — `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` via `$queryRaw`, since Prisma has no first-class API for row-claiming. Must be called inside a transaction; the claim only lasts as long as `tx` stays open.
  - `outbox-publisher.ts`: `OutboxPublisher` polls on an interval (`start()`/`stop()`), claiming+sending+marking **one row per transaction** (not a whole batch in one transaction — a lock is only held for one row's Kafka round trip). `pollOnce()` is exposed directly so tests can drive it deterministically instead of waiting on the timer; it drains the full unpublished backlog but stops immediately on a send failure (that row's `publishingAttempts`/`lastError` are still committed) rather than tight-looping retries with no backoff.
- **The `PENDING -> QUEUED` transition now happens when the publisher confirms delivery, not at creation.** `OutboxPublisher` takes an optional `onPublished(row)` hook, invoked after a row's `publishedAt` commits (outside that transaction — this hand-off is best-effort, not atomic with the commit). `modules/jobs/infrastructure/job-outbox-published.handler.ts` supplies the jobs-specific implementation (`createJobOutboxPublishedHandler(jobRepository)`): for a `JobRequested` row, looks up the job by `aggregateId` and transitions `PENDING -> QUEUED` through the repository — keeping the "jobs module's own repository is the only writer of `Job.status`" rule intact even though the publisher itself lives outside `modules/jobs`. `server.ts` wires this hook and starts/stops the publisher alongside the two consumers.
- **At-least-once, never exactly-once, by design**: if the process dies after Kafka's `send()` acks but before the transaction commits, the row is still unpublished on restart and gets sent again — proven directly in `tests/integration/outbox/outbox-publisher.test.ts` by claiming a row, sending it for real, then throwing inside the transaction instead of letting it commit (simulating the crash without needing to kill the process), then running a real publisher and asserting two deliveries landed on the topic. The same file also proves two concurrent `OutboxPublisher` instances against the same Postgres never claim (and therefore never send) the same row twice.

### Idempotent consumers (Milestone 10)

M9's outbox guarantees at-least-once delivery; this milestone makes redelivery of an already-applied event safe everywhere it could otherwise double-apply.

- **`ProcessedEvent` model** (`prisma/schema.prisma`, table `processed_events`): `id, eventId, consumerName, processedAt`, with `@@unique([eventId, consumerName])`. The unique constraint *is* the concurrency guarantee — two processes racing to insert the same pair (e.g. a brief overlap during a rebalance) get serialized by Postgres; the loser's insert throws `P2002` and is treated as a no-op instead of double-applying.
- **`src/messaging/idempotent-consumer.ts`** exports `withIdempotency({ prisma, consumerName }, apply)`, which wraps a business handler into a `MessageHandler`: parses the message body just far enough to read `eventId` (every envelope has one — see `src/contracts/envelope.ts`), then inside one `prisma.$transaction`, inserts-or-skips the `ProcessedEvent` row and, only if the insert won the race, runs `apply(payload, tx, body)`. Insert and business change commit or roll back together — if `apply` throws, the `ProcessedEvent` insert rolls back too, so the next redelivery retries the business change instead of silently skipping it forever (a check-then-insert-then-apply done as separate statements would lose this).
- **`createConsumer()` (`src/messaging/consumer.ts`) gained an `autoCommit` option** (default `true`, unchanged behavior). Idempotent consumers pass `false`; `createConsumer` then commits each message's offset itself, manually, immediately after `handler` resolves — never before. This ordering is the other half of the safety property: committing the offset first (or via KafkaJS's own interval-based autoCommit) would let a crash between the offset commit and the DB transaction lose the event instead of redelivering it.
- **Both existing consumers are now wrapped**: `modules/jobs/infrastructure/job-status.consumer.ts` and `modules/execution/infrastructure/jobs-requested.consumer.ts` both take a `prisma: PrismaClient` option and pass `autoCommit: false` + a `withIdempotency`-wrapped handler to `createConsumer`. This deliberately relaxes the M4 rule that `prisma-job.repository.ts` is the only file in the jobs module allowed to import the Prisma client: `job-status.consumer.ts` now holds a `PrismaClient` too, needed to open the shared transaction `withIdempotency` commits — but it still never calls `prisma.job.*` itself; every Job-row read/write still goes through `JobRepository`.
- **`JobRepository.findById`/`update` now take an optional second `client` parameter** (`PrismaClient | Prisma.TransactionClient`, aliased as `JobRepositoryClient` in `domain/job-repository.port.ts`), defaulting to the repository's own `this.prisma`. `job-status.consumer.ts`'s `apply` callback passes the transaction it's given straight through, so the job's status transition commits in the exact same transaction as the `ProcessedEvent` insert — without this, a crash between the two could mark an event processed whose job update never actually landed, and it would never be retried. `execution`'s consumer doesn't touch the database at all (per the cross-cutting rule below), so its `apply` callback ignores the `tx` it's handed — the transaction still exists purely to make the `ProcessedEvent` insert atomic with... itself, which is enough: if a later step throws, the insert rolls back and the whole message is safely retried on redelivery.
- **Not yet, deliberately**: no retry/backoff routing — a handler that keeps throwing just leaves the offset uncommitted forever (default KafkaJS redelivery), with no dead-letter path. That's Milestone 11.

### Retry strategy and dead-letter topics (Milestone 11)

Bounded, tiered retries with per-tier delay, exhaustion routing to a dead-letter topic, poison-message handling, and a timeout watchdog — all reusing the same `JobFailed` event rather than inventing a parallel failure path.

- **Envelope gained a `notBefore` field** (`src/contracts/envelope.ts`): `string | null` (ISO datetime), defaulting to `null` ("immediately") in `createEnvelope`. This is how a retry dispatch tells its consumer not to act until a tier's delay has elapsed — it's an envelope-level field (not payload-level) so every event type gets it for free.
- **`JobRequestedPayloadV1` gained `attempt` and `failureHistory`**; **`JobFailedPayloadV1` gained `type`, `payload`, `maxAttempts`, and `failureHistory`** (`src/contracts/events/*.event.ts`, new shared `src/contracts/events/failure-record.ts`). The retry router (below) must be able to decide retry-vs-dead-letter and re-dispatch a job from the `JobFailed` event alone, without ever reading the Job row — execution still never touches the jobs table, so every field it needs to act travels with the event. `failureHistory` accumulates one `{attempt, error, failedAt}` entry per failed attempt, carried forward across every retry hop.
- **`src/contracts/retry-tier.ts`** — `RetryTier = 1 | 2 | 3`, `RETRY_TIER_TOPICS` (`jobs.retry-1/2/3`), and `tierForAttempt()` (clamps at tier 3 even if `maxAttempts` implies more retries than that). Lives under `src/contracts`, not `modules/execution/domain`, specifically because **both** the execution module (dispatches retries) and the jobs module (maps a retry dispatch to the `QUEUED` transition) need it — importing it from `modules/execution/domain` into the jobs module would itself be a module-boundary violation caught by `npm run boundaries`. Same reasoning put the `jobs.dead-letter` topic constant in `src/contracts/topics.ts`.
- **`modules/execution/infrastructure/retry-router.ts`** consumes `jobs.failed` and decides what happens next: `attempt >= maxAttempts` → publish `JobDeadLettered` to `jobs.dead-letter`; otherwise → publish a fresh `JobRequested` (attempt incremented, `notBefore = now + tier delay`) to `jobs.retry-{tierForAttempt(attempt)}`. Never writes the Job row — same as every other execution-side consumer.
- **`modules/execution/infrastructure/process-job-requested.ts`** extracts the "dispatch to the handler, publish `JobStarted`/`JobCompleted`/`JobFailed`" logic that used to live inline in `jobs-requested.consumer.ts` into a shared function, `processJobRequestedBody`, because a retried dispatch is handled identically to the original one — just with a higher `attempt` and accumulated `failureHistory` already sitting in the envelope. Both `jobs-requested.consumer.ts` (topic `jobs.requested`) and the new `retry-tier.consumer.ts` (topics `jobs.retry-1/2/3`, one consumer instance per tier) call it.
- **Poison messages never get thrown.** `processJobRequestedBody` and `retry-router.ts` both `safeParse` the incoming envelope first; a validation failure calls `publishMalformedMessageToDeadLetter` (`modules/execution/infrastructure/dead-letter.ts`) instead of throwing. Throwing would leave the offset uncommitted and retry forever under KafkaJS's default redelivery — blocking the partition on a message that can never parse successfully — and a malformed payload isn't a "retryable" failure to begin with (the roadmap's stated common mistake to avoid). `jobDeadLetteredPayloadSchemaV1` is deliberately looser than `jobFailedPayloadSchemaV1` (nonnegative rather than positive attempt/maxAttempts, nullable `type`) specifically so a poison message with no recoverable job identity can still land in this schema.
- **`retry-tier.consumer.ts`'s delay wait happens *before* entering `withIdempotency`'s transaction, never inside it** — Prisma's default interactive-transaction timeout (a few seconds) would abort a tier-3 wait of many minutes. The wait loop calls the KafkaJS payload's `heartbeat()` every few seconds while waiting, specifically so a long wait doesn't make the broker think the consumer died and trigger a rebalance mid-wait.
- **`modules/jobs/infrastructure/job-status.consumer.ts` now also subscribes to `jobs.retry-1/2/3`**, mapping a retry dispatch to the `FAILED -> QUEUED` transition (the automatic-retry half of the `FAILED --> QUEUED` edge in the state diagram; M12 adds the manual-retry half). **`modules/jobs/infrastructure/dead-letter.consumer.ts`** is a separate consumer/file (its own commit, per the roadmap) mapping `jobs.dead-letter` to `FAILED -> DEAD_LETTERED`; a poison message's synthetic random `aggregateId` simply won't match a real job, so `findById` returning `null` is handled as a no-op, same pattern already used elsewhere.
- **`modules/jobs/infrastructure/timeout-watchdog.ts`** polls for `RUNNING` jobs whose `startedAt` is older than `config.jobTimeoutMs` and publishes a `JobFailed` (`error: 'timeout'`) for each — the *same* event execution would publish on a real handler failure, so it flows through the existing retry-router / job-status-consumer pipeline unchanged; timeout isn't a special case anywhere downstream. It never writes `Job.status` directly (only detects and publishes, preserving the single-writer rule), and keeps an in-memory `Set` of already-flagged job IDs (evicted once a job leaves `RUNNING`) purely to avoid re-publishing every poll tick while waiting for the async pipeline to catch up — not a correctness requirement, since the query filter on `status: 'RUNNING'` is what actually prevents duplicate detection after a restart.
- **New config**: `RETRY_TIER_1_DELAY_MS`/`_2_`/`_3_` (default 30s/5m/30m), `JOB_TIMEOUT_MS` (default 5m), `TIMEOUT_WATCHDOG_POLL_INTERVAL_MS` (default 30s) — all in `src/config/env.ts`, following the existing `envSchema` pattern.
- **No new migration.** The roadmap listed `Job.lastFailureReason` as an *optional* addition; skipped deliberately — `failureHistory` already travels through every Kafka hop and is visible in consumer logs, and `Job.error` still holds the latest error string, so no new column was needed for this milestone's completion criteria.
- **A known, accepted race**: `job-status.consumer.ts` (applying `FAILED` from `jobs.failed`) and `retry-router.ts`/`dead-letter.consumer.ts` (reacting to the same `jobs.failed` event, or to the retry/dead-letter event it produces) are independent consumers with no cross-topic ordering guarantee. In the rare case a downstream transition is attempted before its prerequisite has landed, `Job.transitionTo` throws `IllegalJobStateTransitionError`, the message's offset isn't committed, and KafkaJS's default redelivery retries it — which resolves almost immediately in practice since the prerequisite (same-process, no artificial delay) typically lands first. Not specifically fixed here; proper eventual-consistency handling across independently-ordered topics is Milestone 20's concern, not this one's.

### Cancellation and manual retry (Milestone 12)

`POST /api/jobs/:jobId/cancel` and `POST /api/jobs/:jobId/retry`, both enforcing the state machine through the entity rather than branching in the route or service layer.

- **`Job.cancel()`** (`domain/job.entity.ts`) is the single place cancel's semantics are decided: immediate `transitionTo('CANCELLED')` from PENDING/QUEUED; from RUNNING it only sets a new `cancelRequested: boolean` field (job stays RUNNING) — the entity, not the route, decides which of the two behaviors applies. Every other source state throws `IllegalJobStateTransitionError`, mapped to a 409 by `modules/jobs/api/routes.ts` (a plain `try/catch`; there's no global Fastify error handler, and adding one for just this wasn't warranted). `Job.retry()` similarly only allows FAILED/DEAD_LETTERED → QUEUED, throwing otherwise. `cancelRequested` is cleared back to `false` as part of the `CANCELLED` transition's patch.
- **`JobRepository` gained `updateWithOutboxEvent()`** (mirroring `createWithOutboxEvent` from M9), refactored out of `PrismaJobRepository.update()`'s existing optimistic-concurrency logic (`updateWithClient`, now shared by both). Manual retry needs to transition an *existing* row to QUEUED and insert a fresh outbox `JobRequested` atomically — same "row and delivery guarantee land together or neither does" reasoning as job creation, just for an update instead of an insert. The retried `JobRequested` payload always starts with `failureHistory: []`: unlike the automatic retry router, which has the triggering `JobFailed` event's history sitting right there, a manually-triggered retry has no such event to draw from (the Job row itself never stores accumulated failure history — only the latest `error` string) — this is a deliberate simplification, not an oversight.
- **Cooperative RUNNING cancellation needed a way for a handler to observe cancellation without execution ever reading the Job row.** `JobHandler.execute()` (`domain/job-handler.port.ts`) gained a second parameter, `JobExecutionContext.isCancelled(): Promise<boolean>`; `GenerateReportHandler` accepts but ignores it — its "work" is a single ~10ms delay with no natural tick boundary to check mid-flight, which is the documented, accepted limitation of simulated work the roadmap calls out, not a bug. `modules/execution/domain/cancellation-checker.port.ts` defines `CancellationChecker = (jobId: string) => Promise<boolean>` purely as a type — the real implementation is only ever constructed in `server.ts` (the composition root, which is allowed to reach across modules; the modules themselves are not) and passed down as a plain function, so execution never imports jobs' domain/infrastructure directly.
- **`server.ts`'s `isJobCancelled(jobId)`** checks `job.status === 'CANCELLED' || job.cancelRequested` — both conditions matter and are easy to conflate: the first covers a job cancelled immediately from PENDING/QUEUED (by the time a consumer would dispatch it, its status is already CANCELLED — this is the "consumer checks status-before-dispatch" line from the roadmap, implemented as an early return in `processJobRequestedBody` before publishing `JobStarted`), the second covers a RUNNING job where cancellation was only requested, not yet observed. Checking only `status === 'CANCELLED'` (an earlier draft's mistake, caught before landing) would mean the cooperative RUNNING path could never actually be observed, since a cooperatively-cancelled job never transitions to CANCELLED *until* the handler notices `cancelRequested` and stops itself — checking the wrong field made the mechanism circularly unobservable.
- **`processJobRequestedBody` checks `isCancelled()` twice**: once before dispatch (skip entirely, no events published — covers the PENDING/QUEUED race), and once more right after `execute()` settles (success or failure) — if cancellation was observed by then, a new `JobCancelled` event publishes instead of `JobCompleted`/`JobFailed`, discarding whatever the handler actually returned or threw. A cancelled job never consumes retry budget: retry-router only ever sees genuine `JobFailed` events.
- **New `JobCancelled` event + `jobs.cancelled` topic** (`src/contracts/events/job-cancelled.event.ts`, added to `infrastructure/kafka/create-topics.sh` and every Testcontainers test's own topic list — a test that calls `startJobStatusConsumer` without creating this topic first fails its `consumer.subscribe()` with `KafkaJSProtocolError: This server does not host this topic-partition`, which is exactly how the two M9/M11 e2e suites broke until their topic lists were updated here). `job-status.consumer.ts` subscribes to it, mapping to `RUNNING -> CANCELLED` — already a legal transition, no entity change needed for that half.
- **Same known race as M11's applies here too, unaddressed for the same reason**: a cooperative cancel's `JobCancelled` and a concurrently-in-flight `JobFailed`/`JobCompleted` for the same job are produced by the same consumer instance (not a cross-consumer race like M11's), so in practice this one doesn't manifest — noted for completeness, not because it bit us.
- **Not yet, deliberately**: bulk retry/cancel endpoints (explicitly out of scope per the roadmap).

### Structured logging and correlation IDs (Milestone 13)

One `correlationId` traceable from the HTTP request through every Kafka hop — mostly achieved by centralizing logging in the messaging wrapper rather than adding bespoke log calls to every consumer/handler.

- **`correlationId` now originates at the HTTP layer via Fastify's own request-id mechanism, not a hand-rolled hook.** `src/shared/correlation-plugin.ts` exports `generateCorrelationId`, passed as Fastify's `genReqId` option in `app.ts` (reuses an inbound `x-correlation-id` header if present, generates a UUID otherwise). An earlier draft instead used an `onRequest` hook that reassigned `request.log = request.log.child({ correlationId })` — this looked right but **Fastify's own built-in "incoming request"/"request completed" log lines don't pick it up**, because Fastify captures the logger reference used for those before any user `onRequest` hook runs; only `genReqId` reaches them. Using `genReqId` also means `request.id` *is* the correlationId, so every log line for the request — Fastify's own and anything a route logs via `request.log` — carries it for free, with no plugin/hook needed at all.
- **`JobService.createJob()`'s `CreateJobInput` gained an optional `correlationId`**, used instead of always calling `randomUUID()` internally; `modules/jobs/api/routes.ts` passes `request.id`. A caller that constructs a job directly (tests, scripts) without one still gets a fresh UUID — the parameter is additive, not required.
- **The messaging wrapper logs automatically, so individual consumers/handlers don't have to.** `src/messaging/producer.ts`'s `publish()` and `src/messaging/consumer.ts`'s `createConsumer()` both gained an optional `logger`; `publish()` logs one `'event published'` line per send, and `createConsumer()` logs one `'event consumed'` line per message *and* passes a per-message child logger (already bound to that message's correlation fields) to the handler as `payload.logger`, via a new `MessagePayloadWithLogger` type. `src/messaging/envelope-log-fields.ts` reads `eventId`/`eventType`/`aggregateId`/`correlationId`/`causationId` off an `unknown` value defensively (not via the zod schema) so it logs whatever's on the wire, including a not-yet-validated malformed message. Every `startXConsumer`/`OutboxPublisher`/`TimeoutWatchdog` constructor took a new optional `logger` param purely to thread this through from `server.ts`; none of them had to add a single explicit log call themselves — `job-status.consumer.ts` and `dead-letter.consumer.ts` in particular get full lifecycle logging for free since they only consume, never publish, and `createConsumer`'s auto-log already covers that side.
- **`src/shared/logger.ts` gained a `Logger` interface (`info`/`error`/`child`) and a `noopLogger`, deliberately narrower than `pino.Logger`.** This sidesteps the same FastifyBaseLogger-vs-concrete-pino-instance variance quirk already documented in `modules/jobs/api/routes.ts` (M5) — every function that takes an optional `logger` in this milestone types it as this narrower `Logger`, not `pino.Logger`, so passing `app.log` (typed `FastifyBaseLogger`) from `server.ts` type-checks without another `AnyLogger`-style workaround. `noopLogger` is the fallback used when a `logger` wasn't supplied (mainly tests constructing a handler directly, e.g. `withIdempotency`'s existing Testcontainers tests that build an `EachMessagePayload` by hand — `logger` on that type is optional specifically so those tests didn't need to change).
- **`causationId` propagation was *not* new work here** — every execution-side publish already set `causationId: envelope.eventId` since M11/M12 (retry-router, process-job-requested, dead-letter). The roadmap lists it under M13, but it was already fully wired; this milestone's actual gap was the logging/correlationId-origin piece above.
- **`buildApp()`'s `BuildAppDeps` gained an optional `logger: pino.Logger`**, overriding the instance `createLogger(config)` would otherwise build — the hook that lets tests supply the "pino test transport" the roadmap's own M13 test asks for. `tests/helpers/capturing-logger.ts` builds a real `pino` instance writing to an in-memory `Writable` and exposes `lines()` (each captured line parsed as JSON) for assertions.
- **Tests**: `tests/jobs/correlation.test.ts` (no Docker) asserts one correlationId appears in both the HTTP access log and the outbox row's envelope payload, and that an inbound `x-correlation-id` header is honored. `tests/integration/messaging/kafka.foundation.test.ts` gained a case asserting `publish()`/`createConsumer()`'s automatic logging directly against a real broker. `tests/integration/e2e/job-lifecycle.e2e.test.ts` gained a case that greps the Kafka-side log capture by one job's correlationId and asserts the causally-guaranteed ordering (published precedes its own consumption; started precedes completed) — it deliberately does **not** assert a total order between `job-status.consumer.ts`'s consumption of `jobs.started` and `jobs-requested.consumer.ts`'s publish of `jobs.completed`, since those are independent consumer groups with no ordering guarantee between them (the same known race M11/M12 already documented).

### Metrics and Grafana (Milestone 14)

`GET /metrics` (prom-client, Prometheus text format) plus a Prometheus + Grafana stack in `docker-compose.yml`, instrumented at the same application-service boundaries earlier milestones already established rather than adding metrics calls scattered through every handler.

- **`src/shared/metrics.ts`** owns a dedicated `client.Registry()` instance (not prom-client's global default registry) specifically so repeated module loads across test files never collide with a "metric already registered" error — `client.collectDefaultMetrics({ register: metricsRegistry })` runs against that same instance. It exports five instruments: `jobDurationSeconds` (histogram, `type`+`outcome` labels), `jobsTotal` (counter, `status` label), `retryTotal` (counter, `tier` label), `deadLetterTotal` (counter, no labels), `outboxBacklog` (gauge, no labels). **Labels are deliberately type/status/tier only, never `jobId`** — per-job labels would create an unbounded, ever-growing set of time series, the exact "common mistake" the roadmap calls out.
- **`app.ts`'s `GET /metrics` route** sets `Content-Type` from `metricsRegistry.contentType` and returns `metricsRegistry.metrics()` — no auth/allowlisting added, matching the roadmap's scope (this is a portfolio project, not a hardened deployment).
- **`jobsTotal` is incremented only in `modules/jobs/infrastructure/job-status.consumer.ts` and `dead-letter.consumer.ts`** — the same two files that are already the sole writers of `Job.status` (see the cross-cutting rule), so the counter and the actual persisted status can never drift apart: one `.inc({ status })` call sits immediately after each `jobRepository.update(job.transitionTo(...))`.
- **`jobDurationSeconds` is observed in `modules/execution/infrastructure/process-job-requested.ts`**, timing from immediately before `executeJobService.execute()` to whichever of the three outcomes actually lands (`succeeded`/`failed`/`cancelled`), via `process.hrtime.bigint()` rather than `Date.now()` for sub-millisecond monotonic precision unaffected by wall-clock adjustments. This is the "application-service boundary" the roadmap's architectural note means: the same function already handles both the original dispatch and every retry-tier redispatch, so instrumenting it once covers all of them without touching `jobs-requested.consumer.ts` or `retry-tier.consumer.ts` individually.
- **`retryTotal` is incremented in `retry-router.ts`** right after a retry is published to its tier topic (label = the tier `tierForAttempt()` picked), and **`deadLetterTotal` is incremented inside `publishDeadLetter()`** (`modules/execution/infrastructure/dead-letter.ts`) — the single choke point both the retry-router's exhaustion path and `publishMalformedMessageToDeadLetter`'s poison-message path already funnel through, so one `.inc()` call covers both without duplicating it at each call site.
- **`outboxBacklog` is set once per `OutboxPublisher.pollOnce()` cycle**, after the claim-and-publish loop drains, via a new `countUnpublished()` in `src/outbox/outbox.repository.ts` (a plain `outboxEvent.count({ where: { publishedAt: null } })` — no raw SQL needed here, unlike the row-claiming query). Deliberately reuses the publisher's existing poll cadence instead of adding a second, independent polling loop — the roadmap explicitly warns against polling the backlog too aggressively, and a second query loop against the same table would be exactly that mistake.
- **docker-compose additions**: `prometheus` (scrapes `host.docker.internal:3000/metrics` per `infrastructure/prometheus/prometheus.yml`, since the app runs on the host via `npm run dev` rather than as its own compose service — `extra_hosts: host.docker.internal:host-gateway` makes that resolve on Linux too, not just Docker Desktop) and `grafana` (anonymous admin access for local dev, provisioned via `infrastructure/grafana/provisioning/{datasources,dashboards}` pointing at the checked-in `infrastructure/grafana/dashboards/eventforge.json`). Grafana is mapped to host port `3001` — `3000` is already the app's port.
- **Tests**: `tests/shared/metrics.test.ts` is a Docker-free smoke test (`buildApp()` + `InMemoryJobRepository`, same pattern as `tests/jobs/job.routes.test.ts`) asserting `GET /metrics` returns Prometheus text format containing all five metric names. `tests/integration/e2e/job-lifecycle.e2e.test.ts`'s existing SUCCEEDED-path case gained an assertion that `jobsTotal`'s `SUCCEEDED` sample increased, proving the instrumentation is actually wired into the real consumer, not just unit-testable in isolation.
- **Not yet, deliberately**: alerting rules, PagerDuty-style integration — same as the roadmap states.

### Testcontainers integration tests (Milestone 15)

Every integration/e2e test file already used Testcontainers directly since M6 — this milestone's actual change is booting one shared Postgres + one shared Kafka container for the *entire* `test:integration` run instead of one pair per file, plus two new tests that need a real, killable child process.

- **`tests/integration/containers.ts`** holds the two container-boot functions (`startPostgresContainer`, which also runs `prisma migrate deploy` against the fresh DB; `startKafkaContainer`, the same Confluent-image + log-message-wait-strategy setup every file used individually before) and `PRODUCTION_TOPICS` (the 9 real topic names, mirroring `infrastructure/kafka/create-topics.sh`'s list).
- **`tests/integration/setup.ts`** is the actual `globalSetup`/`globalTeardown` implementation: boots both containers once, creates every production topic, and hands connection info to the (separate-process) Jest workers via `process.env.TEST_DATABASE_URL`/`TEST_KAFKA_BROKERS` — env vars set in `globalSetup` are inherited by workers since they're spawned afterward. Container *handles* (needed for `.stop()` in `globalTeardown`) go on `globalThis` instead, since `globalSetup` and `globalTeardown` run in the same parent Jest process and share that object — the standard Testcontainers+Jest pattern. Individual test files never construct their own container; they call `sharedDatabaseUrl()`/`sharedKafkaBrokers()` in their own `beforeAll`. **`tests/integration/global-setup.ts`/`global-teardown.ts` are thin wrapper files that only re-export `setup.ts`'s named exports as `default`** — Jest's `globalSetup`/`globalTeardown` config keys each independently `require` a file's default export, so one physical file can't serve both roles; the roadmap's named `setup.ts` holds the real logic, these two just adapt it to Jest's shape.
- **`globalSetup`/`globalTeardown` don't go through Jest's `moduleNameMapper`** — they're loaded outside the normal per-test module registry, so the `@/` alias silently fails to resolve there (`Cannot find module '@/messaging/kafka-client'`) even though it works everywhere else. `setup.ts` uses a plain relative import instead, with a comment explaining why, rather than trying to make the alias work in a context it fundamentally can't.
- **The sharp edge this design trades in for faster, hermetic runs: topics (and their message history) are no longer fresh per file.** A `fromBeginning: true` consumer against a *production* topic name (which can't be renamed per-file — the real consumers under test hardcode `'jobs.requested'` etc.) will replay every message any earlier file in the same run published to that topic, not just this test's own. `tests/integration/execution/retry-and-dead-letter.e2e.test.ts` already had the right pattern for this (`consumeMatching`: filter by a predicate — e.g. this test's own `aggregateId` — rather than resolving on the first message received); `jobs-requested.consumer.test.ts`'s simpler `consumeOne` didn't, and broke exactly this way the first time the whole suite ran against a shared broker (a `'job-success-1'`-style fixed aggregateId, first-message-wins consumer picked up a stale message from a file that ran earlier). Fixed by giving it the same predicate-matching pattern, with a `randomUUID()` aggregateId per test run instead of a fixed string. **Any new ad-hoc consumer against a shared production topic needs this same filtering** — "first message wins" is only safe against a topic this one test created itself with a unique, per-test name (e.g. `` `_dev.foo-${randomUUID()}` ``).
- **`jest.config.js`'s `maxWorkers` is now unconditionally `1`, not `process.env.CI ? 1 : 2`.** The M9-era reasoning for 2 workers locally (each Testcontainers file's own container boot was the dominant cost, and 2 workers overlapped that boot time without starving the CPU) no longer applies now that container boot happens once, globally. What replaces it as the reason to serialize: several real consumers (`job-status.consumer.ts`, `retry-router.ts`, `jobs-requested.consumer.ts`, the retry-tier consumers, ...) use **hardcoded, production consumer-group IDs** — two integration test files racing concurrently against the *same* shared broker with the *same* group ID would have Kafka's own rebalance protocol split partitions between them, each silently stealing messages meant for the other's assertions. Full serialization sidesteps this entirely rather than trying to make every file's group IDs unique (which would mean diverging from the real production IDs the tests are supposed to exercise).
- **`tests/integration/fixtures/idempotent-consumer-process.ts`** is a standalone consumer, spawned as a real OS child process (via `npx tsx`, not `ts-jest`) by the two new tests below — needed because you can't `SIGKILL`/`SIGTERM` the Jest process itself to simulate a crash. It reuses the real `createConsumer` + `withIdempotency` wrappers (not a stand-in), so what the tests prove is the actual production crash-safety property, not a synthetic imitation of it. It talks to its parent over stdout as newline-delimited JSON (`{"event": "processing-start"/"processing-done", "eventId": ...}`), configured entirely via `FIXTURE_*` env vars so the parent can control its topic, group, per-message delay, and (for the rebalance test) a short `sessionTimeout`/`heartbeatInterval` — `createConsumer` (`src/messaging/consumer.ts`) gained optional passthroughs for both, unused by every real call site, purely so this fixture can shrink Kafka's ~30s default failure-detection window down to a few seconds.
- **`tests/integration/fixtures/spawn-fixture.ts`'s `spawnConsumerFixture()` had to solve a process-tree problem, not just a spawn-and-signal one.** `npx tsx <file>` is itself 2–3 processes deep (npx's own shell shim, the tsx CLI, and the actual Node process tsx re-execs with its loader flags) — signaling only the immediate child (`child.kill()`) leaves the real consumer process (and its live Kafka connections) running as an orphan, which is exactly what caused `npm run test:integration` to hang after all tests had already passed ("Jest did not exit one second after the test run has completed"). Fixed by spawning with `detached: true` (making the child its own process-group leader) and signaling the whole group via `process.kill(-child.pid, signal)` — the negative PID is what targets the group, not just one process in it.
- **`tests/integration/messaging/consumer-rebalance.test.ts`**: publishes 4 messages to a fresh single-partition topic, starts fixture A with a 10s per-message delay, waits for its `processing-start` on message 0 (proving it holds that offset uncommitted), `SIGKILL`s it, starts fixture B in the same group, and asserts B alone processes all 4 messages exactly once (`ProcessedEvent` row count == 4, unique `eventId`s, and A never emitted a single `processing-done`). A single partition is deliberate — it makes "which consumer owns everything" and thus "no duplicate side effects" unambiguous, rather than reasoning about a partial partition split.
- **`tests/integration/messaging/graceful-shutdown.test.ts`**: same fixture, but `SIGTERM` instead of `SIGKILL`, and the fixture registers no signal handler at all — the point being tested is that the system is safe *even without* a graceful drain, since `createConsumer`'s autoCommit-after-handler design (M10) means an in-flight message's offset was never going to commit regardless of how the process died. Asserts the `ProcessedEvent` row doesn't exist and (via `admin.fetchOffsets`) that Kafka reports `'-1'` (no committed offset) immediately after the kill, then starts a fresh fixture in the same group and asserts it reprocesses that exact message.
- **Not yet, deliberately**: a CI matrix across OS/Node versions (a single Linux/Node LTS target is sufficient per the roadmap).
- **`tests/integration/messaging/kafka.foundation.test.ts`'s two `it`s got their per-test Jest timeout bumped from 120s to 180s** after the first real CI run under the shared-broker setup failed at 120.686s on the second test — just barely over. By the time that file runs, the shared broker (2 vCPUs on GitHub's hosted runner) has already handled group-join/rebalance traffic from every earlier file's consumer groups in the same run, which a brand-new consumer group's initial join apparently feels more than the other suites do. No logic bug found; widening the timeout was the proportionate fix given every other file (including both new fixture-process tests) passed cleanly on the same run.

## Architecture

### Module boundary rule (the load-bearing constraint)

`src/modules/{jobs,execution,notifications,audit}/` each have an internal `api/ → application/ → domain/ → infrastructure/` slice. **A module may only be reached through its own `api/` folder (or through Kafka events) — never by importing another module's `application/`, `domain/`, or `infrastructure/` directly.** `shared/` may not depend on any module.

This is enforced mechanically by `.dependency-cruiser.cjs` (`npm run boundaries`), not just by convention — it will fail the build on a violation, including in CI. The reason this rule exists: the roadmap's whole arc is extracting `execution` (then `notifications`, then `audit`) into standalone services later without a rewrite. Every cross-module interaction has to already be Kafka-events-only or api-surface-only, from the very first line of code, or the later extraction turns into a rewrite. If you're about to import from `../../other-module/domain/...`, that's the boundary rule stopping you — the fix is to go through Kafka or that module's `api/`, not to add an exception to the dependency-cruiser config.

`shared/` is for cross-cutting technical code only (logger, generic result types, etc.) — never business logic. Business logic belongs inside a module.

### Target folder layout

```
src/
├── app.ts         # buildApp() — pure, testable, no listen()
├── server.ts      # entrypoint: listen() + graceful shutdown
├── config/        # env/config loading
├── db/            # database wiring
├── messaging/     # Kafka producer/consumer wrapper
├── outbox/        # transactional outbox publisher
├── shared/        # cross-cutting technical utilities only
└── modules/
    ├── jobs/           # job management: API, state machine, persistence (authoritative for Job status)
    ├── execution/      # job execution: handler registry, Kafka consumers (never writes Job status directly)
    ├── notifications/  # job-completion notifications
    └── audit/          # append-only audit trail
```

`prisma/schema.prisma` + `prisma/migrations/` live at the repo root (not under `src/`); `generated/prisma/` (the generated client) is gitignored.

### Key design decisions to preserve as milestones land

- **PostgreSQL is authoritative for job state; Kafka only transports events.** The `jobs` module's own status consumer is the only writer of `Job.status` — `execution` (and later services) must never update the Job row directly, even before it's extracted into its own service. This is what makes the eventual service extraction a deployment change instead of a rewrite.
- **Event contracts (`src/contracts`, introduced at Milestone 6) are built ahead of need**, isolated from day one, because they become `packages/event-contracts` unchanged when the monorepo split happens at Milestone 18.
- **Two distinct "idempotency" mechanisms exist (or will) and must not be conflated**: an HTTP `Idempotency-Key` header for duplicate job submissions (delivered, Milestone 5 — see `DuplicateJobSubmissionError`), and a Kafka `ProcessedEvent(eventId, consumerName)` table for duplicate event delivery (Milestone 10). Different tables, different concerns.
- **The outbox pattern guarantees at-least-once delivery, never exactly-once** — there's a real gap between a Kafka send succeeding and the outbox row being marked published. Consumers are idempotent _because_ of this, not despite it.
- Prisma has no first-class `SELECT ... FOR UPDATE SKIP LOCKED` — the outbox publisher's row-claiming needs `$queryRaw`.

### TypeScript config notes

- Path alias `@/*` maps to `./src/*` (see `tsconfig.json`); mirrored in `jest.config.js`'s `moduleNameMapper`.
- `moduleResolution: "Node16"` is paired with `module: "Node16"` deliberately (TypeScript 6 deprecated the old `"Node"`/`baseUrl` combination) — don't reintroduce `baseUrl` or revert to `moduleResolution: "Node"`.
- `tsconfig.build.json` extends the base config, restricts `include` to `src`, and excludes `**/*.test.ts` — that's the one used by `npm run build`; the base `tsconfig.json` (via `npm run typecheck`) covers both `src` and `tests`.
